# USB input power with a POWER-Z KM003C

The POWER-Z KM003C is a USB-C meter that sits in a board's USB power.
`tools/power/km003c_ptest.py` polls it while a power-test image runs its
sweep, then joins the capture windows to the firmware's results. It needs
`pyusb` and `pyserial`; the packet layout follows
[km003c-rs](https://github.com/okhsunrog/km003c-rs).

## Set up

- Install libusb (`brew install libusb`, or `libusb-1.0-0` on Linux) and
  `pip install pyusb pyserial`. On Linux, give your user access to USB device
  `5fc9:0063` with a udev rule. The kernel's `powerz` hwmon driver binds the
  same interface; the tool detaches it.
- Close POWER-Z's own app: only one program can claim the meter.
- Wire it: computer port to meter input, meter output to board, and the
  meter's data port to the computer. Powering the board from the computer through the
  meter keeps the board's USB serial console reachable.

## Power-test images for other boards

`CONFIG_MUSE_POWER_TEST` also builds for the Waveshare 1.75C and 2.16 and the
AIPI Lite. They share `boards/board_power_test_generic.c`, a backend on
`muse_board_t` with its own matrix: a subset of the Watcher's peripheral rows (fixed CPU
clocks, display, codecs, Wi-Fi scanning) plus static white frames, which carry
the brightness cost on AMOLED panels, and an animation row. There is no sleep matrix,
deep sleep or dry run; those report unsupported. From `esp32/`:

```sh
profile=waveshare-s3-175c   # or waveshare-s3-216, aipi
idf.py -B build-${profile}-power-test -DIDF_TARGET=esp32s3 \
  -DSDKCONFIG=build-${profile}-power-test/sdkconfig \
  -DSDKCONFIG_DEFAULTS="sdkconfig.defaults;devices/sdkconfig.muse;devices/sdkconfig.muse-${profile};devices/sdkconfig.muse-${profile}-power-test" build
```

These boards use the native USB Serial/JTAG console. Their overlays set
`CONFIG_USJ_NO_AUTO_LS_ON_CONNECTION`, which holds a no-light-sleep lock while
a USB host is attached, so their DFS baselines report skipped. Brightness and panel sleep are requested settings with no hardware
readback. Records carry codec history and ES8311/ES7210 register snapshots
read outside the capture windows. `cold` is reported only after a power-on
reset. Opening the console resets the chip through USB, and after that reset
the record keeps the saved history (`suspended` after an earlier run on the
same power-up) or says `unknown` when there is none, for example right after
flashing. If a board's `audio_init` fails after
starting I2S (AIPI Lite enables its channels before probing the codec), the
run ends as `error`: reset the board before the next one.

## Run

```sh
python3 tools/power/km003c_ptest.py --console PORT --output board-usb5v.jsonl
```

The tool arms with `"usb_powered":1`: the sweep starts without unplugging USB
and accepts only the peripheral matrix. It waits `--boot-wait-s` (20 s) after
opening the console, which can reset the board, and requests 5 s settling and
20 s capture per state by default. The meter is polled at 20 Hz; 1 s is
dropped from each edge of a window. `>ptest.status` and `>ptest.abort` work
mid-run. On the Watcher, whose console is a UART, the image can light-sleep
in the DFS baseline rows and miss commands sent then: a missed abort leaves
the run going until it ends, and the next arm reports `already_active`
(reset the board to stop it sooner). The tool maps result timestamps to host time using the arm
acknowledgement and periodic status replies.

The JSONL starts with the arm acknowledgement and firmware results, followed
by window summaries in uA plus `mean_vbus_v` and `mean_power_mW`. Meter errors,
windows with fewer than 80 % of the expected samples after guards, and
incomplete or mismatched results cause a non-zero exit after saving the
collected data. If the tool fails while the firmware run may still be going,
it sends `>ptest.abort` first. Use a new output path for each run; existing
files are never overwritten.

### Charging off on AXP2101 boards

With a battery fitted, its charge current shows up on the 5 V input. On the
Waveshare 1.75C and 2.16, `--charging-off` adds `"charging_off":1`: at run
start the image clears AXP2101 register `0x18` bit 1 and verifies the
readback. Charging is restored, with readback, on finish, abort, error and at
the next boot of this image. A guard task retries every 5 s once the run's
`max_duration_ms` plus 60 s has passed, and a run where it fired ends as
`error` with `ESP_ERR_TIMEOUT`.
The key is implemented for the AXP2101 only; AIPI Lite and the Watcher
reject it.

**Warning:** the bit survives ESP32 resets. Per the AXP2101 datasheet (REG 18,
section 6.5.4.5) only a PMU system reset or power-on reset sets it back,
and the normal firmware does not write it. If a run is cut and other firmware
is flashed before this image boots again, charging stays off until this image
boots once or the PMIC is reset.

### ESP-Mosaico over ESP-Iris

Mosaico uses its existing USB-C ESP-Iris connection; no UART adapter.
Build with the pinned S31 IDF and Vibe Mode checkout described in
[the board guide](../../devices/README.md#espressif-esp-mosaico-experimental). Set `MUSE_POWER_TEST=1`
when running `tools/muse/board.sh build mosaico`. The diagnostic overlay
loads last and uses a separate build directory. Match the board's retained
partition table before installing a bundle.

Select the board with `--iris-device-id`, the workspace containing
`mosaico.py` with `--mosaico-workspace`, and the meter with `--meter-serial`.
The workspace defaults to `MOSAICO_WORKSPACE` when set, otherwise
`~/mosaico/esp-mosaico-vibe`. The host validates the device ID and workspace
before opening the meter or creating the output file.
In another terminal in that workspace, keep
`python3 mosaico.py iris run --device-id "$DEVICE_ID"` running, with
`DEVICE_ID` set to the same board ID. This retains a Gateway client between
RPCs. Without it, the Gateway's 10 s idle shutdown can overlap the
collector's 10 s polling interval.
Use `--capture-ms 30000 --guard-s 5` to retain 20 s per window, or
`--capture-ms 40000 --guard-s 10` for wider timing guards. Avoid heavy host
work during capture; the collector rejects captures whose clock uncertainty
exceeds the guard.
The [Mosaico results](usb5v-findings.md#esp-mosaico-2026-11-08)
record the measured fixture and firmware revision.

The adapter invokes `mosaico.py iris rpc` through the managed Gateway.
RPC service `0x5054` queues PTEST commands, reads output chunks and reads the
gauge. Boot tokens and byte offsets reject stale or missing output;
a new reader starts at the live tail. Commands are not automatically retried.
Arm acknowledgements and result retrieval allow 120 s for chunked replies.
The collector waits for a complete status reply, then 10 s before polling
again. An outstanding reply keeps its original clock anchor.
The host records clock uncertainty and rejects it above the edge guard.

Before arming, the BQ27220 must report 100% and current within 2 mA of zero.
Gauge RPCs return `ESP_ERR_INVALID_STATE` from arm through finish/abort
restoration, without reading I2C during the run.
`--charging-off` is unsupported. The backend uses the Iris USB link for USB
presence, ES8311 address `0x19`, no ES7210, and adds the 320 MHz fixed-clock
row. Iris holds a no-light-sleep lock throughout the diagnostic: these are
USB-input measurements, including Iris, with no battery sleep measurement.

## Comparing with battery-side numbers

USB changes each load differently, by where it sits in the board's power
tree, so neither absolute values nor steps between states can be used as
battery numbers directly. As general rules:

- **Behind a switching regulator** the same work draws less input current at
  a higher input voltage.
- **On a linear regulator or straight on the input rail** the current stays
  roughly the same.
- **Powered only by USB** (a USB-UART bridge, the charger IC) a load adds a
  contribution that is absent on battery.

On the Watcher, a USB sweep with the battery removed (2026-10-09, Watcher
power-test image with `usb_powered`; image hash not recorded) against the
PPK2 run on its battery terminals
([sensecap-watcher-profile.csv](sensecap-watcher-profile.csv)) gives these
steps:

| Step | Supply in the Watcher schematic | USB | Battery | Ratio |
|---|---|---|---|---|
| CPU 40 to 240 MHz | VCC_3V3, buck U7 from VCC_IN | +15.1 mA | +18.6 mA | 0.81 |
| Backlight 0 to 100% | LCD_3.3V, switched from VCC_3V3 | +32.3 mA | +36.0 mA | 0.90 |
| First codec open and close | Codec_3V3, LDO U10 from VCC_IN | -34.9 mA | -35.1 mA | 1.00 |

The two steps behind the buck are smaller on USB; the step on the LDO is not.
The schematic does not explain why the backlight's ratio is higher than the
CPU's. Read the board's schematic for where each load sits before using a USB
number.

## Known limitations

- **It measures the 5 V USB input**, not the battery: the board plus its
  charger, regulators and any battery charging. Measure with the battery full,
  with `--charging-off`, or with no battery fitted, and check the charging
  acknowledgement in the header.
- **A computer on USB is not battery use.** USB input includes the bridge,
  charger and console activity. On the Watcher with its battery removed, a
  fit over the 22 shared states other than Wi-Fi scanning gives
  `I_USB = 5.9 mA + 0.92 * I_battery` (1.8 mA RMS; with Wi-Fi scanning,
  6.3 mA + 0.91, 2.5 mA RMS). These are coefficients for those loads and
  fixtures, not a constant parasitic current. In the awake rows, USB input
  power was 1.19 to 1.47 times the battery-side power, a whole-board ratio
  across separate fixtures, not a converter efficiency. Compare variants on the same setup; measure at the
  battery connector for battery-life estimates.
- **Replugging USB can change the baseline.** After the meter's input was
  moved to a charger and back, the Watcher, powered off on USB, drew about
  36 mA at the USB input for about a minute and then about 166 mA. Keep USB
  connected for a whole series and repeat the first variant at the end, or
  take the battery out.
- **It samples; it does not catch short bursts.** The tool takes single
  readings at 20 Hz, about 360 per window. That is enough for the window
  means of steady states, which repeat within the run-to-run figures in
  [usb5v-findings.md](usb5v-findings.md), but peaks shorter than the gap
  between readings are not seen. Use a PPK2 for transients.
- **Orientation.** A meter plugged in the other way round reads negative
  current; the tool summarises its magnitude.
- **AIPI Lite's `charging`** comes from its charge-status pin and battery
  ADC. With no battery fitted it means nothing and varies between records.
